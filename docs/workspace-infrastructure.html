Infrastructure Blueprint

Local-first Infrastructure for the Workspace

이 문서는 Main Workspace, Interaction Pipeline를 실제로 받쳐줄 인프라 구조를 설명한다. 목표는 처음부터 분산 시스템을 짓는 것이 아니라, `혼자서 안정적으로 쓰기 좋은 로컬 우선 인프라`를 만들고 필요한 지점만 점진적으로 외부 서비스와 연결하는 것이다.

Recommended posture
앱은 로컬에서 돌아가고, 데이터는 로컬에 남기고, 백업과 동기화만 별도 레이어로 분리한다.
즉, runtime과 source of truth는 로컬. 클라우드는 복제와 공유를 위해서만 쓴다.

1

원칙

처음부터 복잡한 인프라를 만들면 시스템보다 운영 비용이 더 커진다.

이 시스템은 팀용 SaaS보다 개인용 운영체계에 가깝기 때문에, `고가용성`보다 `낮은 마찰`, `빠른 복구`, `문맥 보존`, `에이전트 친화성`이 더 중요하다. 따라서 인프라 설계도 서버 중심이 아니라 `로컬 워크스테이션 중심`으로 가는 편이 맞다.

Local-first 실행과 저장의 기준은 로컬 머신이다.
Composable Personal OS, Workspace, Knowledge를 느슨하게 연결한다.
Event-friendly 기능 호출보다 이벤트 로그와 후처리에 강한 구조가 좋다.
Recoverable 실패했을 때 로그, 스냅샷, 백업으로 복구 가능해야 한다.
2

런타임 계층

실제 인프라는 역할에 따라 5개 레이어로 나누는 것이 가장 명확하다.

Layer 1 Interface Tauri 또는 로컬 웹 UI. 사람이 보는 화면과 에이전트 진입점.
Layer 2 Control Plane project registry, session orchestration, command routing.
Layer 3 Memory Plane mem0, LLM wiki (knowledge/wiki/ — raw/ 자료를 에이전트가 합성), session logs, decision ledger.
Layer 4 Execution Plane 에이전트 실행, 파일 접근, 명령 실행, ingestion jobs.
Layer 5 Sync / Backup Git, cloud backup, encrypted snapshot, optional remote mirror.
2A

시스템 아키텍처

한눈에 보면 이 시스템은 `로컬 앱 코어 + 분리된 기억 계층 + 느슨한 백업 계층` 구조다.

SVG Overview

읽는 순서는 좌상단에서 우하단이다. `UI/Agent`가 `Workspace Core`에 붙고, 코어는 실행 서비스와 저장 계층을 제어하며, 외부는 백업과 동기화만 담당한다.

Integrated System Map

통합 맵에서 `Main Workspace`가 중심에 있는 이유는 모든 것을 소유해서가 아니라, 세 시스템 사이의 흐름을 조정하기 때문이다. `Personal OS`는 우선순위를 밀어 넣고, `Workspace`는 실행하며, `Knowledge System`과 `mem0`는 세션 결과 중 남겨야 할 것만 각각 가져간다.

아키텍처 관점에서 가장 중요한 규칙은 이것이다. `로컬 스토리지가 기준 시스템이고, 외부 레이어는 복제본과 안전장치일 뿐`이다. 이 점이 흐려지면 sync 충돌과 운영 복잡도가 빠르게 커진다.
3

저장소 설계

가장 중요한 결정은 데이터를 하나의 DB에 다 집어넣지 않는 것이다.

권장 저장소 분리

Storage 용도 추천 형태
Operational DB task, project, goal, session index, action queue SQLite 또는 PGlite. 이후 필요하면 Postgres로 승격.
Knowledge Store 구조화된 장기 문서, ADR, 도메인 노트, PDF · 참고 자료, LLM 합성 wiki Obsidian vault 안에 두 계층.
projects/{slug}/ — 사람이 직접 쓰는 ADR, 개념, 레퍼런스. YAML frontmatter가 source of truth. PGlite knowledge_index는 파생 검색 캐시.
wiki/ — 에이전트가 raw/ 자료를 읽고 합성한 페이지. 전역 하나, frontmatter project_id 태그로 필터링.
Memory Store mem0용 사용자 선호, 반복 패턴, 개인 문맥 Qdrant (Mac Docker, ~/workspace/data/mem0/) — 벡터 저장소.
Ollama on Pi 5 — LLM 추론 (gemma2:2b 기억 추출, nomic-embed-text 임베딩).
mem0ai (npm) — 앱과 Qdrant·Ollama를 연결하는 어댑터. 대화 종료 후 비동기로 기억 추출·저장.
Event Log session lifecycle, routing events, sync history append-only JSONL 또는 DB event table.
Artifact Store 첨부 이미지, exports, snapshots, generated files 로컬 파일 시스템.

왜 분리하나

  • 운영 데이터와 지식 데이터를 같은 스키마에 섞으면 진화가 어렵다.
  • mem0 성격의 데이터는 일반 업무 테이블과 관리 규칙이 다르다.
  • event log는 수정보다 추적과 복구가 중요하다.
  • 파일 아티팩트는 DB보다 파일 시스템이 단순하다.

초기 디렉터리 예시

~/workspace/ raw/ ← LLM wiki 입력 드롭 존 (.gitignore) shared/ ← 프로젝트 무관 자료 personal-os/ ← 프로젝트 힌트 (선택) knowledge/ ← Obsidian vault 루트 wiki/ ← LLM 합성 페이지 (전역 하나) index.md log.md [topic].md ← frontmatter: project_id: [personal-os, ...] projects/ personal-os/ ← 사람이 직접 쓰는 노트 adr/ concepts/ references/ attachments/ shared/ ← 프로젝트 무관 공통 지식 playbooks/ data/ ← 런타임 데이터 (.gitignore) db/ app.db ← PGlite (tasks, goals, knowledge_index) sessions/ sessions.jsonl snapshots/ mem0/ artifacts/ ← 생성 파일 (.gitignore) screenshots/ exports/ generated/ backups/ ← 백업 (.gitignore) daily/ weekly/
4

서비스 구성

서비스는 많이 둘수록 좋은 게 아니라, 분리 이유가 분명할 때만 추가해야 한다.

처음부터 필요한 것

UI runtime Tauri 또는 localhost 기반 Next 앱.
Local DB runtime SQLite/PGlite를 직접 임베드.
Job runner ingestion, backup, sync, summarization 같은 백그라운드 작업.
File indexer 프로젝트 카드 기준으로 파일/폴더 메타데이터 스캔.

나중에 붙이면 되는 것

Vector search 지식 검색 정확도가 부족해질 때만 추가.
Remote Postgres 여러 기기 실시간 동기화가 정말 필요할 때.
Message queue 작업량이 많고 비동기 후처리가 복잡해질 때.
Shared API server 혼자 쓰는 단계에서는 대부분 불필요.
5

동기화와 백업

동기화와 source of truth는 같은 개념이 아니다. 이 둘을 분리해야 데이터가 안정된다.

추천 전략

  • 로컬 DB는 주기적으로 스냅샷 백업.
  • knowledge 폴더는 Git으로 버전 관리.
  • artifacts와 snapshots는 날짜 기반 압축 백업.
  • 복구 우선순위는 `DB → knowledge → artifacts → cache` 순으로 정의.
  • 동기화는 pull/push보다 `export/import + conflict review`가 더 안전할 수 있다.

피해야 할 것

  • DB 파일을 Dropbox/iCloud와 실시간 동기화하는 것
  • mem0와 wiki를 같은 백업 정책으로 다루는 것
  • 실행 중 DB를 바로 원격 미러링하는 것
  • 복구 절차 없이 백업만 쌓아두는 것
6

보안

개인 시스템이라도 에이전트가 파일과 명령에 접근하므로 권한 경계는 필요하다.

권한 분리

  • workspace는 프로젝트 경로를 등록하되, 모든 경로를 기본 허용하지 않는다.
  • 에이전트별로 읽기 전용과 편집 가능 경로를 나눈다.
  • secret은 OS keychain 또는 별도 env vault에 둔다.
  • 승인 없는 destructive action은 막는다.

로그 위생

  • session log에는 API key, 토큰, 민감 원문을 남기지 않는다.
  • knowledge 승격 전 민감정보 필터를 둔다.
  • 백업 파일 암호화 여부를 단계별로 결정한다.
7

권장 단계

한 번에 완성하려 하지 말고 3단계로 가는 편이 현실적이다.

Phase 1

Single-machine 로컬 DB, local files, simple job runner, manual backup.

Phase 2

Structured sync knowledge Git sync, scheduled DB snapshots, mem0 export/import.

Phase 3

Optional remote mirror 원격 읽기용 복제본이나 여러 기기용 sync coordinator 추가.
8

최소 스택

지금 시작한다면 이 정도가 가장 균형이 좋다.

Recommended minimum stack

Concern Recommendation
App shell Tauri + local React UI
Operational data SQLite or PGlite
Knowledge documents Obsidian vault — 마크다운, PDF, 첨부파일, 링크, 태그, 검색 포함
Memory layer mem0 with its own store
Search Start with lexical/file index, add vector later only if needed
Background work single local job runner + cron-style scheduler
Backup DB snapshots + Git for docs + encrypted archive for artifacts

한 줄 결론

당신에게 맞는 인프라는 `작은 로컬 운영체제`에 가깝다. 즉, 서버 팜이 아니라 `한 대의 노트북 위에서 안정적으로 실행되고 복구되는 control plane`을 먼저 만드는 게 맞다.

9

Raspberry Pi 활용 아이디어

항상 켜져 있어야 하는 역할을 MacBook 대신 Pi에 위임한다.

이 아키텍처에서 Pi가 자연스럽게 들어갈 수 있는 자리는 항상 켜져 있어야 하는 것들이다. MacBook은 닫히거나 자지만 Pi는 계속 돌아가기 때문에, Sync/Backup 레이어와 백그라운드 서비스를 분리하기에 적합하다.

🟢 확정: mem0 LLM 추론 서버

Ollama 상시 서빙 Pi 5에서 Ollama를 항상 띄워둠. Mac이 꺼져 있어도 기억 추출 대기 가능.
gemma2:2b — 기억 추출 대화 종료 후 "기억할 내용" 추출용. Pi 5에서 ~15-20 tok/s. 비동기라 체감 없음.
nomic-embed-text — 임베딩 기억 저장·검색 시 벡터화. 경량 모델로 Pi에서도 빠름.
API 비용 0 Gemini API 대신 로컬 추론 → mem0 관련 LLM 호출 비용 없음.

🟢 확정: 인프라 역할 분담

Pi 5 — Ollama 추론 http://raspberrypi.local:11434 — LAN으로 Mac에서 접근. 네트워크 레이턴시 ~2ms.
Mac — Qdrant (Docker) 벡터 저장소는 Mac에서 실행. 데이터는 ~/workspace/data/mem0/에 영구 보존.
mem0ai (npm) — 어댑터 Personal OS 앱에서 Qdrant + Ollama를 연결. 대화 후 비동기로 기억 추출·저장·조회.
오프라인 fallback Pi 미연결 시 mem0 기억 추출 skip, 기존 기억 조회는 Mac Qdrant로 가능.

Job Runner · 백그라운드 서비스

주기적 DB 스냅샷 백업 cron으로 PGlite 스냅샷을 Pi에 저장. 앱이 꺼져 있어도 백업 동작.
Knowledge System Git sync knowledge 폴더를 Pi에서 주기적으로 pull/push.
Session log ingestion · 요약 JSONL 로그를 Pi에서 수집하고 주기적으로 요약 생성.

MCP 서버로 Claude Code 연결

로컬 네트워크 MCP 서버 Pi를 MCP 서버로 띄우면 MacBook Claude Code 세션에서 Pi 데이터에 직접 접근 가능.
Context Snapshot 관리 "오늘 context snapshot 가져와", "이 결정과 관련된 ADR 검색해줘" 같은 요청을 Pi가 처리.
세션 시작/종료 자동화 session_started · session_closed 이벤트를 Pi 쪽에서 처리하고 관련 데이터 라우팅.

항상 켜진 Knowledge 서버

LLM wiki index 서빙 Knowledge System의 문서 인덱스를 항상 쿼리 가능한 상태로 유지.
rebuild-index 스케줄 knowledge/projects/ 변경 감지 → knowledge_index 자동 갱신.
