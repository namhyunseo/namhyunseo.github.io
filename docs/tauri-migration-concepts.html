1큰 그림: 웹앱 vs 데스크탑앱

가장 먼저 잡아야 할 건 구조의 차이입니다. 웹앱은 화면과 데이터가 네트워크(HTTP)로 떨어져 대화하지만, 데스크탑앱은 한 프로그램 안에서 직접 호출로 대화합니다.

지금 (웹앱)

브라우저 화면 (React)
  ↕ fetch /api/... (HTTP)
Next 서버 (Route Handler)
  ↕ pg
Postgres (도커)
→

목표 (데스크탑앱)

웹뷰 화면 (React 그대로)
  ↕ 앱 내부 호출
Rust 코어 / 내장 DB
  ↕
PGlite (앱 안에 내장)
핵심 정의 데스크탑 전환 = "네트워크 너머의 서버+DB"를 "앱 안의 코어+내장DB"로 끌어들이는 일. 화면(React)은 거의 그대로, 그 뒤의 배선이 바뀝니다.

2Tauri의 정체

Tauri는 웹 화면을 전용 앱 창에 담고, 컴퓨터 기능을 붙여주는 틀입니다. 두 덩어리로 이뤄져요.

  • 웹뷰(WebView) — 보이는 화면. OS에 내장된 브라우저 엔진을 빌려 씀(맥은 WebKit). 여기에 네 React UI가 뜸.
  • Rust 코어 — 파일·메뉴·알림 등 브라우저가 못 하는 일을 담당하는 "일꾼".
비유 Tauri = 액자(창) + 만능 일꾼(Rust). 액자엔 기존 웹 화면을 끼우고, 일꾼에게 "이 PDF 열어줘", "파일 저장해줘"를 시킨다.

Electron과 비교 (왜 Tauri를 골랐나)

항목TauriElectron
방식OS 내장 웹뷰 빌려씀크롬 브라우저 통째로 번들
앱 용량수~십 MB100MB+
백엔드 언어RustNode.js
대표 앱신생, 가벼움 지향VS Code, Slack, Discord
네 경우 혼자 쓰는 가벼운 로컬 앱이라 Tauri가 적합. 기존 React UI를 재활용할 수 있어 진입장벽도 낮음. Rust는 거의 안 배워도 됨 — 흔한 기능은 플러그인으로 제공.

3"서버가 사라진다" — Route Handler의 운명

이번 전환에서 비용의 80%가 여기 있습니다. 네 앱의 /api/... Route Handler 15개+는 "서버 코드"인데, 데스크탑앱엔 띄워둘 서버가 없습니다. 이 로직을 어디론가 옮겨야 해요.

옮길 곳 선택지

방법설명난이도
앱 내부(프론트)로DB 호출을 화면 코드에서 PGlite로 직접 (개인앱이라 가능)중
Rust 커맨드로민감하거나 네이티브가 필요한 로직만 Rust로상
Node 사이드카Next 서버를 앱 안에서 함께 실행(임시 다리)중
주의 "API 라우트"라는 개념이 데스크탑에선 흐려집니다. 화면 → (HTTP) → 서버 패턴을 화면 → (직접 호출) → 데이터 로 다시 생각해야 함. 가장 손이 많이 가는 부분.

4프론트엔드: 정적 SPA로 만들기

Tauri 창이 띄우는 건 결국 HTML/JS 묶음입니다. Next.js의 서버 렌더링 기능에 기대지 않고, 빌드하면 정적 파일로 떨어지는 SPA(단일 페이지 앱) 형태가 이상적이에요.

SPA란 서버가 매번 페이지를 그려주는 게 아니라, 한 번 받은 JS가 브라우저 안에서 화면 전환을 다 처리하는 방식. 데스크탑앱과 궁합이 좋음.
네 경우 이미 화면이 거의 단일 클라이언트 페이지(page.tsx)라 부담이 적은 편. 서버에 의존하던 데이터 fetch 경로만 "내장 DB 호출"로 바꾸면 됨.

5데이터: Postgres(도커) → PGlite(내장)

사용자한테 "도커 켜세요"는 불가능하니, DB를 앱 안으로 내장해야 합니다. 여기서 PGlite가 핵심 카드예요.

PGlite란 "진짜 Postgres를 WASM으로 컴파일해 앱 안에서 돌리는" 내장 DB. 별도 서버·도커 없이 파일 하나로 동작.
네게 결정적으로 유리 너는 pg raw SQL을 쓰는데, PGlite는 Postgres SQL을 거의 그대로 받음. → queries.ts를 갈아엎지 않아도 됨. (SQLite로 갔다면 전면 재작성이었음.) RAG의 코사인 계산도 순수 JS라 그대로 동작.

바뀌는 것

  • db.ts의 연결 부분을 pg 풀 → PGlite 인스턴스로 교체
  • 마이그레이션(schema_migrations) 실행 방식 이식
  • 데이터 저장 위치가 도커 볼륨 → 앱 데이터 폴더의 파일로

6JS ↔ Rust 다리: IPC / command

화면(JS)이 네이티브 기능(Rust)을 쓰려면 둘을 잇는 다리가 필요한데, 이걸 IPC(프로세스 간 통신), 호출 단위를 command라고 부릅니다.

비유 화면이 주방(Rust)에 주문표(command)를 넣으면, 주방이 요리해서(파일 읽기 등) 접시(결과)를 돌려준다. JS에선 invoke("read_file", ...) 처럼 부름.

알아둘 것

  • JS와 Rust는 다른 프로세스 → 주고받는 데이터는 JSON으로 직렬화됨
  • 비동기(await)로 동작 — 기존 fetch 감각과 비슷
  • 흔한 기능(파일·대화상자·알림)은 직접 안 짜고 공식 플러그인을 부름

7비밀키와 보안 모델

웹앱에선 Gemini 키를 서버에 숨겨 두었죠. 데스크탑앱엔 그 "서버 뒤"가 없어서 생각을 바꿔야 합니다.

  • 앱에 박힌 문자열은 마음먹으면 추출 가능 — 진짜 비밀은 클라이언트에 못 숨김
  • 개인용 단일 사용자라면 키를 로컬 설정/OS 키체인에 두고 거기서 호출하면 충분
  • 배포해서 남이 쓴다면 → 키를 각자 입력하게 하거나 별도 프록시 서버를 둠
네 경우 혼자 쓰니 OS 키체인 또는 로컬 설정 파일에 Gemini 키를 두는 방식으로 단순하게 가면 됨.

8OAuth: 리다이렉트 → 루프백

Google 캘린더 같은 OAuth는 "로그인 후 지정한 URL로 되돌아오는" 방식인데, 데스크탑앱엔 돌아올 웹 주소가 없습니다. 이게 전환에서 가장 까다로운 한 군데예요.

루프백(loopback) 방식 앱이 잠깐 localhost의 임시 포트로 작은 수신기를 열어 두고, 브라우저 로그인 후 그 주소로 인증 코드를 받아오는 데스크탑용 표준 흐름.
주의 Google Cloud 콘솔에서 클라이언트 유형을 "데스크톱 앱"용 리다이렉트로 다시 설정해야 함. 코드뿐 아니라 외부 설정도 바뀜.

9네이티브 능력 & 권한 모델

데스크탑으로 가는 진짜 보상이 이 부분이에요. 브라우저가 막아두던 일들을 할 수 있게 됩니다.

  • 파일 시스템 읽기/쓰기, Finder 드래그&드롭, .pdf·.png 파일 연결
  • 메뉴바, 트레이 상주, 전역 단축키(⌘K 캡처), 시스템 알림
  • 네이티브 미리보기, 오프라인 동작
권한(capabilities) 모델 Tauri는 안전을 위해 "이 앱은 이 폴더만, 이 기능만 쓸 수 있다"를 설정으로 명시하게 함. 기본은 잠겨 있고 필요한 것만 열어주는 방식.

10빌드 · 서명 · 배포

웹은 push하면 끝이지만, 데스크탑앱은 설치 파일을 만들어 배포하는 단계가 새로 생깁니다.

  • 번들링 — 앱을 .app/.dmg 같은 설치물로 묶음
  • 코드 서명/공증(notarization) — 맥이 "확인된 개발자"로 인정하게 하는 절차 (Apple 개발자 계정 $99/년)
  • 자동 업데이트 — 새 버전을 사용자에게 내려주는 장치(원할 때)
네 경우 (혼자 쓰기) 서명·공증·자동업데이트 전부 건너뛰어도 됨. 빌드한 앱을 처음 한 번 "우클릭 → 열기"로 실행하면 그만. 남에게 배포할 때만 서명을 추가하면 됨.

11용어 사전 (빠른 참조)

WebView (웹뷰)
OS에 내장된 브라우저 엔진. Tauri 창이 네 화면을 여기에 띄움.
Rust 코어 / 백엔드
네이티브 기능을 담당하는 앱의 일꾼. 파일·메뉴·DB 접근 등.
IPC
프로세스 간 통신. 화면(JS)과 코어(Rust)가 데이터를 주고받는 통로.
command / invoke
JS가 Rust 기능을 부르는 단위와 호출 함수.
SPA
한 번 받은 JS가 브라우저 안에서 화면 전환을 다 처리하는 단일 페이지 앱.
PGlite
Postgres를 WASM으로 만든 내장 DB. 서버·도커 없이 앱 안에서 동작.
사이드카(sidecar)
앱과 함께 실행되는 보조 프로세스(예: Node 서버를 임시로 같이 띄우기).
capabilities
이 앱이 어떤 파일/기능에 접근할 수 있는지 정하는 Tauri의 권한 설정.
코드 서명 / 공증
OS가 앱을 신뢰하게 만드는 인증 절차. 배포 시 필요.
루프백 OAuth
localhost 임시 포트로 인증 코드를 받는 데스크탑용 로그인 흐름.

12학습 체크리스트

작업 들어가기 전에 "이게 무슨 말인지 안다"고 말할 수 있으면 충분합니다.

  • 웹앱의 "화면↔서버↔DB(네트워크)" 구조와, 데스크탑의 "화면↔코어↔내장DB(직접호출)" 구조의 차이를 설명할 수 있다
  • Tauri가 웹뷰 + Rust 코어로 이뤄지고, Electron보다 가벼운 이유를 안다
  • 내 /api Route Handler들이 데스크탑에선 "옮겨야 할 로직"이라는 걸 이해한다
  • PGlite가 왜 내 queries.ts를 거의 살려준다는지 안다
  • JS가 Rust를 invoke로 부르는 IPC 개념을 안다
  • 앱에 박은 키는 숨겨지지 않으며, 개인용이면 로컬 보관으로 충분함을 안다
  • Google OAuth가 루프백 방식 + 콘솔 재설정이 필요함을 안다
  • 혼자 쓰면 코드 서명·자동업데이트를 건너뛸 수 있음을 안다
