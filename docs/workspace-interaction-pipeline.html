Interaction Pipeline

How the Three Systems Work Together

이 문서는 Personal OS, Knowledge System, Main Workspace가 서로 어떤 순서로 상호작용해야 하는지를 파이프라인으로 정리한다. 핵심은 세 시스템을 섞는 것이 아니라, 각자의 역할을 보존한 채 이벤트로 연결하는 것이다.

Core idea
판단은 Personal OS에서, 실행은 Workspace에서, 학습은 Knowledge System에서 일어나야 한다.
mem0는 그 사이에서 사용자 고유의 선호와 반복 패턴을 기억하는 보조 메모리 계층이다.

1

역할 모델

세 시스템이 동일한 데이터를 동시에 소유하면 결국 충돌한다.

이 구조에서 Personal OS는 `무엇을 할지`를 정하고, Main Workspace는 `어떻게 시작할지`를 준비하며, Knowledge System은 `무엇을 남길지`를 축적한다. mem0는 작업 성향과 선호를 기억해 다음 실행의 질을 높인다.

Source of truth

Personal OS goal, priority, project status, review decision
Main Workspace session, next start, decision log, handoff, context snapshot
Knowledge System projects/{slug}/ — 사람이 직접 쓴 ADR, 개념, 레퍼런스 (source of truth)
wiki/ — 에이전트가 raw/ 자료에서 합성한 페이지 (전역, project_id 태그 필터링)
UI는 Obsidian vault
mem0 preference, habit, recurring work pattern, collaboration style

한 문장씩 요약

  • Personal OS는 방향과 우선순위를 결정한다.
  • Main Workspace는 실제 실행 진입점을 제공한다.
  • Knowledge System은 재사용 가능한 지식만 장기 보관한다. UI는 Obsidian vault.
  • mem0는 개인적인 작업 방식과 선호를 학습한다.
2

메인 루프

이 구조는 `Capture → Plan → Execute → Distill → Review` 순환으로 보는 것이 가장 명확하다.

1 Capture 아이디어, 링크, 메모, 할 일을 먼저 workspace inbox에 받는다.
2 Plan Personal OS가 우선순위를 정하고 workspace가 실행 문맥을 준비한다.
3 Execute 작업은 항상 workspace에서 시작하고 에이전트는 여기에 붙는다.
4 Distill 세션 종료 후 결과를 action, knowledge, memory로 분류한다.
5 Review 주간 리뷰에서 세 시스템을 다시 맞춘다.
메인 워크스페이스는 이 루프의 중심 허브이지만, 모든 정보를 직접 소유하지는 않는다. 허브이자 라우터이지 최종 저장소는 아니다.
3

실행 파이프라인

Planning과 Execution이 만나는 지점이 실제 사용감의 대부분을 결정한다.

Pipeline by stage

Stage Who leads What happens
Capture Main Workspace 새 입력을 inbox로 받고 `actionable`, `knowledge`, `memory-candidate`로 1차 분류
Plan Personal OS goal과 task 우선순위를 정하고, 해당 항목을 project card와 연결
Execute Main Workspace 경로 진입, 관련 파일 확인. knowledge/projects/{slug}/(사람 노트)와 knowledge/wiki/(LLM 합성, project_id 필터링), mem0 컨텍스트 로드
Distill Main Workspace 세션 결과를 task 업데이트, knowledge 승격 후보, mem0 후보로 나눔
Review Personal OS 우선순위 재정렬, 열린 루프 정리, 승격된 지식 점검

중요 원칙

  • 실행 중 발생하는 모든 메모를 곧바로 Knowledge System에 쓰지 않는다.
  • 먼저 Workspace 로그에 쌓고, 세션 종료 후 장기 가치가 있는 것만 승격한다.
  • Personal OS는 실행 중간 상태보다 우선순위와 완료 여부만 신경쓴다.
  • mem0는 개인적이고 반복적인 패턴만 받는다.

이 파이프라인을 실제로 돌리는 저장소, 큐, 백업 계층은 Infrastructure Blueprint를 참고.

4

세션 복구

중단 후 재진입 비용을 낮추는 것이 workspace 설계의 실질적인 핵심이다.

Context Snapshot structure

session_id: ws-2026-06-02-001
project: personal-os
current_state: local routing cleanup in progress
next_start: verify dashboard task grouping
watchouts:
  - queries.ts and local-router.ts are both changing
references:
  - README.md
  - docs/main-workspace-control-plane.html
decisions:
  - keep project files outside workspace
  - promote only stable knowledge to wiki

왜 중요한가

  • 다음 세션에서 설명을 다시 쓰지 않아도 된다.
  • 에이전트가 중단 맥락을 재로딩할 수 있다.
  • 작업 중이던 파일, 결정, 리스크가 함께 복구된다.
5

정제와 승격

세션 종료 후 어떤 정보를 어디로 올릴지 결정하는 단계가 가장 중요하다.

Action으로 보내는 것

  • 완료 상태 변경
  • 다음 액션 생성
  • 블로커 등록
  • 우선순위 재평가 요청

도착지: Personal OS

Knowledge로 보내는 것

  • 재사용 가능한 설계 원칙 → projects/{slug}/concepts/
  • 아키텍처 결정과 이유 → projects/{slug}/adr/
  • 도메인 개념 정리 → projects/{slug}/concepts/
  • 반복 참고할 운영 절차 → playbooks/
  • 외부 자료(논문·문서) → raw/ 에 드롭 → 에이전트가 wiki/에 합성

도착지: Obsidian vault. 사람이 직접 쓰는 것은 projects/, 에이전트가 합성하는 것은 wiki/.

Memory로 보내는 것

`나는 보통 어떤 방식으로 더 잘 일하는가`, `이 프로젝트에서 무엇을 반복적으로 선호하는가`, `비슷한 작업이 오면 미리 기억해두면 좋은 것은 무엇인가` 같은 항목만 mem0에 넣는다. 사실 기록을 다 넣는 것이 아니라, 다음 행동의 질을 높일 패턴만 남기는 것이 맞다.
확정된 mem0 인프라 — 대화 종료 후 mem0ai(npm)가 비동기로 기억 추출 요청. 추론은 Pi 5 Ollama (gemma2:2b 기억 추출 · nomic-embed-text 임베딩), 저장은 Mac Qdrant (Docker, ~/workspace/data/mem0/). LLM API 호출 비용 없음. Pi 미연결 시 추출 skip, 기존 기억 조회는 Qdrant에서 직접 가능.
6

공유 엔티티

세 시스템이 공통으로 이해해야 하는 최소 엔티티만 정해두면 구조가 훨씬 단단해진다.

Entity 주요 소유자 다른 시스템과의 연결
Project Personal OS / Workspace 우선순위와 실제 경로를 연결
Goal Personal OS 세션과 태스크가 왜 존재하는지 설명
Task Personal OS Workspace 세션의 직접적인 시작점
Session Workspace 실행 중 발생한 상태와 로그 저장
Decision Workspace 필요시 Knowledge System의 ADR로 승격
Knowledge Note Knowledge System 다음 세션에서 다시 불러올 구조 문서가 됨
7

이벤트 예시

이벤트 이름을 미리 정해두면 자동화와 에이전트 규칙이 쉬워진다.

대표 이벤트

  • task_prioritized → workspace가 project card 준비
  • session_started → mem0 + wiki context 로드
  • decision_recorded → knowledge 승격 후보 생성
  • session_closed → snapshot 저장, next start 갱신
  • project_completed → 회고와 장기 교훈 정리

자동화 포인트

  • 작업 종료 시 자동으로 다음 시작점 제안
  • 반복적으로 등장한 패턴만 mem0 후보로 올리기
  • 결정 로그 중 구조 관련 항목만 wiki 승격 후보로 표시
  • 우선순위 변경 시 관련 프로젝트 카드에 상태 배지 갱신
8

일상 시나리오

하루 단위로 보면 이 구조는 `판단 → 실행 → 학습` 루프로 읽힌다.

아침

  • Personal OS가 오늘의 우선순위를 정한다.
  • 가장 중요한 프로젝트를 workspace로 보낸다.

작업 중

  • Workspace가 경로, 기억, 에이전트 프로필을 로드한다.
  • 결정과 중간 상태는 session log에 쌓인다.

작업 후

  • 결과는 action, knowledge, memory로 정제된다.
  • 주간 리뷰에서 세 시스템이 다시 맞춰진다.

결국 좋은 구조는 세 시스템을 합치는 구조가 아니라, 메인 워크스페이스가 세 시스템 사이를 오가며 일을 흐르게 만드는 구조다.
