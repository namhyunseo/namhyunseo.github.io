Main Workspace Blueprint

Main Workspace as Control Plane

이 문서는 `main workspace`를 또 하나의 거대한 폴더가 아니라, 흩어진 프로젝트와 기억 시스템 위에 놓이는 실행 허브로 정의합니다. 목표는 파일 위치를 기억하는 일을 줄이고, 작업 진입 비용과 에이전트 문맥 세팅 비용을 함께 낮추는 것입니다.

One-line definition
모든 프로젝트와 기억 시스템 위에 놓이는, 에이전트 중심의 실행 허브
파일 저장소가 아니라 `작업 시작`, `문맥 불러오기`, `기억 라우팅`, `재진입`을 담당하는 운영 레이어.

1

정의

메인 워크스페이스는 파일을 모으는 장소가 아니라 일을 시작하는 인터페이스여야 한다.

좋은 `main workspace`는 실제 프로젝트를 한 폴더 안에 집어넣지 않습니다. 대신 프로젝트의 `위치`, `목적`, `실행 방법`, `관련 기억`, `다음 시작점`을 등록해서 어디서든 같은 진입 경험을 제공하는 `control plane` 역할을 합니다.

project registry agent context memory routing session replay
2

시스템 경계

`Personal OS`, `Knowledge System`, `Main Workspace`는 역할이 겹치면 안 된다.

Decision Layer Personal OS

무엇이 중요한지 정리한다. 우선순위, 계획, 리뷰, 목표 관리가 중심이다.

질문: 지금 무엇을 해야 하는가?

Knowledge Layer Knowledge System

무엇을 알고 있는지 축적한다. 구조화된 개념, 레퍼런스, 장기 문서가 중심이다.

질문: 내가 무엇을 알고 있는가?

Execution Layer Main Workspace

실제로 작업을 시작한다. 프로젝트 진입, 문맥 호출, 에이전트 연결, 세션 복구를 맡는다.

질문: 지금 어디로 진입해야 하는가?

3

왜 필요한가

문제는 파일이 흩어진 것보다, 작업 진입 문맥이 흩어진 데 있다.

기존 방식

  • 프로젝트 위치를 직접 기억해야 함
  • 에이전트를 폴더마다 새로 붙여야 함
  • 문맥을 매번 설명하거나 파일 경로를 다시 줘야 함
  • 중단 후 재진입 비용이 큼
→

원하는 방식

  • 프로젝트는 어디 있어도 등록만 되어 있으면 됨
  • 작업 시작 명령 하나로 경로와 기억을 함께 로드
  • 세션 로그와 다음 시작점이 자동으로 연결됨
  • 에이전트가 사람 대신 진입 절차를 기억함

Main Workspace가 실제로 해야 할 일

프로젝트 위치 추상화 실제 디렉터리는 흩어져 있어도 카드로 하나의 목록에서 접근
에이전트 문맥 표준화 프로젝트별 기본 규칙, 참고 문서, 최근 결정 자동 연결
세션 재진입 최적화 마지막 상태와 다음 행동을 저장해 재시작 비용 감소

설계 원칙

실제 코드 저장소와 분리 프로젝트는 기존 위치 유지. 워크스페이스는 메타데이터만 관리.
장기 지식과 단기 컨텍스트 분리 wiki는 안정적인 지식, logs는 지금 진행 중인 상태.
폴더보다 엔티티 중심 `project`, `session`, `decision`, `problem` 단위로 다룬다.

Project card example

name: personal-os
path: /Users/you/personal-os
type: product
status: active
commands:
  dev: pnpm dev
  test: pnpm test
context_sources:
  - llm_wiki: personal-os
  - mem0: preferences, recent-decisions
key_files:
  - README.md
  - docs/roadmap.md
agent_profile: coding-agent
next_start: "finish local routing cleanup and verify dashboard state"
5

mem0 / LLM wiki 역할 분담

둘 다 기억 시스템이지만 저장 대상이 달라야 충돌이 없다.

Layer 무엇을 저장하나 예시
mem0 개인 선호, 작업 습관, 반복 패턴, 다음에도 기억하면 좋은 맥락 React에서 과한 추상화를 싫어함, 회의 요약은 action item 중심 선호
LLM wiki 안정적인 개념, 시스템 구조, 프로젝트 설명, 장기 보존 가치가 있는 문서 아키텍처 문서, 데이터 흐름, 명명 규칙, 의사결정 기준
Main Workspace 작업 시작 시 무엇을 불러오고, 끝나고 무엇을 어디에 남길지 라우팅 현재 세션에서 wiki 2개와 mem0 키 3개를 호출하고 종료 후 결정 로그 분기

이 역할 분담이 실제로 어떻게 순환하는지는 Interaction Pipeline 문서에서 이어서 볼 수 있고, 이를 받치는 저장소와 서비스 구조는 Infrastructure Blueprint에서 볼 수 있다.

6

운영 흐름

작업 시작부터 종료까지 같은 루틴을 강제하면 에이전트 품질이 안정된다.

Start Session routine

Step 1 프로젝트 카드 선택 이름만 고르면 경로, 실행 명령, 관련 파일을 확보
Step 2 기억 소스 로드 mem0 선호와 LLM wiki 구조 문서를 함께 호출
Step 3 에이전트 프로필 적용 코딩, 글쓰기, 리서치 중 해당 작업 방식으로 진입
Step 4 세션 종료 로그 저장 다음 시작점과 주요 결정을 남기고 필요한 기억만 승격
7

활용 아이디어

중요한 건 기능 수보다 재사용 가능한 작업 인터페이스를 만드는 것이다.

Project Card System 실제 경로 대신 프로젝트 카드로 진입. 위치를 기억하지 않아도 됨.
Context Snapshot 중단 시점, 다음 액션, 주의점, 참고 파일을 짧게 저장.
Agent Entry Point `start coding on personal-os` 같은 진입 명령을 표준화.
Decision Ledger 무엇을 했는지보다 왜 그렇게 정했는지 기록.
Cross-project Dashboard 진행 중 프로젝트, 열린 루프, 보류 이슈를 한 화면에서 확인.
Playbook Library 디버깅, 글쓰기, 리서치, 회고를 반복 가능한 절차로 축적.
8

피해야 할 설계

통합을 명목으로 또 다른 혼잡한 폴더를 만들면 실패한다.

모든 프로젝트 파일을 workspace 아래로 옮기는 것
실제 산출물, 로그, 노트, 지식을 한 저장소 안에 섞는 것
mem0와 LLM wiki에 같은 내용을 중복 저장하는 것
프로젝트 카드 없이 단순 폴더 링크만 모으는 것
프로젝트마다 에이전트 진입 방식이 제각각인 것
