Folder Structure

Workspace Root Folder Design

워크스페이스는 루트 폴더 하나로 관리한다. 앱 코드, Obsidian vault, 런타임 데이터, 아티팩트, 백업이 각자의 자리를 가지며, project slug가 Personal OS의 task/goal 데이터와 Obsidian의 지식 폴더를 연결하는 조인 키 역할을 한다.

핵심 원칙
코드는 git, 지식은 Obsidian, 데이터는 data/ — 그리고 project slug로 세 시스템이 연결된다.

2

앱 ↔ 워크스페이스 연결

personal-os 앱은 워크스페이스 밖 별도 위치에 있고, 환경변수로 워크스페이스 경로를 참조한다.

📦

personal-os/

~/personal-os/ ← 워크스페이스와 독립적 위치
git repo
  • src/Next.js · Tauri 앱 소스코드
  • docs/이 설계 문서들 (HTML). 코드와 같은 repo에서 관리.
  • public/앱 정적 자산
  • .claude/Claude Code 설정, hooks, 프로젝트 메모리
  • .env.local워크스페이스 경로 설정. git에 넣지 않는다.

.env.local 설정

앱이 워크스페이스 위치를 알 수 있도록 경로를 환경변수로 주입한다.

# 워크스페이스 루트
WORKSPACE_ROOT=~/workspace

# 파생 경로 (앱이 계산)
# DB_PATH = $WORKSPACE_ROOT/data/db/app.db
# KNOWLEDGE = $WORKSPACE_ROOT/knowledge
# SESSIONS = $WORKSPACE_ROOT/data/sessions

WORKSPACE_ROOT 하나만 설정하면 나머지는 앱이 자동으로 파생한다. 다른 머신에서 경로가 달라도 이 값만 바꾸면 된다.

물리적 위치 vs 논리적 연결

앱 코드와 워크스페이스 데이터를 분리하면, 앱을 재설치하거나 코드를 갈아엎어도 ~/workspace/의 지식과 DB는 안전하게 남는다. 반대로 워크스페이스 경로가 바뀌어도 .env.local만 수정하면 된다.
3

knowledge/

Obsidian vault. 각 파일의 YAML frontmatter가 소스 오브 트루스이며, DB 인덱스는 여기서 파생된다.

🔮

knowledge/

$WORKSPACE_ROOT/knowledge/
Obsidian vault
  • wiki/ LLM이 raw/ 자료를 읽고 자동 생성·유지하는 합성 페이지들. 전역 하나. 각 페이지 frontmatter에 project_id 태그로 필터링.
  • 00_inbox/ 프로젝트 미정 메모, 링크. 나중에 projects/ 하위로 승격.
  • projects/{slug}/ 사람이 직접 쓰는 지식. Personal OS의 project slug와 폴더명 일치. 하위에 adr/, concepts/, references/, attachments/ 구성.
  • shared/ 프로젝트 독립적 공통 지식. 범용 개념, 공통 레퍼런스.
  • playbooks/ 반복 운영 절차. 배포, 백업 복구, 장비 세팅 등.

두 계층의 역할 구분

wiki/ — LLM 작성
raw/ 자료에서 합성. 프로젝트 태그로 필터링.
projects/{slug}/ — 사람 작성
내 결정, ADR, 직접 정리한 개념.

모든 문서는 frontmatter를 가진다

메타데이터가 파일 안에 있기 때문에 파일 하나가 완결된다. DB가 날아가도 파일에서 복구 가능.

Project Slug — 세 시스템의 조인 키

Markdown frontmatter가 소스 오브 트루스. DB 인덱스는 파생물로 언제든 재빌드 가능.

DB 스키마 (파생 인덱스)

CREATE TABLE knowledge_index ( id TEXT PRIMARY KEY, project_id TEXT, -- slug와 일치 type TEXT, -- adr|concept|ref|playbook tags TEXT, -- JSON array summary TEXT, -- frontmatter의 summary file_path TEXT, -- 실제 .md 파일 경로 indexed_at TIMESTAMP );

이 테이블은 절대 직접 수정하지 않는다. 항상 markdown 파일을 수정하고 인덱스가 따라온다.

에이전트 세션 시작 흐름

-- 1. Personal OS에서 task/goal 로드 SELECT * FROM tasks WHERE project_id = 'personal-os' AND status = 'active'; -- 2. 같은 slug로 지식 인덱스 조회 SELECT summary, file_path FROM knowledge_index WHERE project_id = 'personal-os' ORDER BY type, indexed_at DESC; -- 3. file_path로 실제 내용 로드
에이전트 동작 Personal OS DB Knowledge (Markdown + Index)
세션 시작 active tasks, goals 쿼리 knowledge_index에서 slug로 관련 문서 조회 → file_path로 내용 로드
설계 결정 내림 decision log에 기록 frontmatter 포함한 .md 파일 생성 → 인덱스 자동 갱신
세션 종료 task 상태 업데이트, next_start 갱신 새 지식은 .md 파일로 저장 (인덱스가 따라옴)
인덱스 손상 / 분실 영향 없음 rebuild-index 실행 → frontmatter 스캔으로 재빌드
새 프로젝트 추가 project row 생성 (slug 지정) knowledge/projects/{slug}/ 폴더 생성
핵심 규칙: knowledge_index는 파생 테이블이다. markdown 파일이 source of truth이고 DB는 검색을 빠르게 하기 위한 캐시다. slug는 영문 소문자 + 하이픈만 사용한다 — Personal OS project slug, Obsidian 폴더명, knowledge_index.project_id가 모두 같은 값을 가져야 한다.
4

data/

런타임 데이터. git에 넣지 않는다. 이 폴더가 날아가도 코드와 지식은 살아있다.

🗄️

data/

$WORKSPACE_ROOT/data/
git 제외
db/

app.db — PGlite / SQLite.
tasks, goals, projects, session index, action queue.
knowledge_index — Markdown frontmatter에서 파생된 검색 인덱스. 재빌드 가능.
주기적으로 backups/에 스냅샷.

sessions/

sessions.jsonl — 세션 이벤트 로그.
snapshots/ — Context Snapshot 파일.
다음 세션 시작 시 재로드.

mem0/

mem0 store.
개인 작업 패턴, 선호, 반복 습관.
Raspberry Pi에서 호스팅 가능.

5

artifacts/

실행 중 생성된 파일들. 자동 생성물이라 git에 넣지 않는다.

📎

artifacts/

$WORKSPACE_ROOT/artifacts/
git 제외
  • screenshots/에이전트가 찍은 화면 캡처
  • exports/앱에서 내보낸 리포트, 데이터 파일
  • generated/AI가 생성한 코드, 문서, 기타 결과물

artifacts vs knowledge

artifacts/ knowledge/
자동 생성, 임시적 직접 작성, 장기 보관
날짜별 정리 주제별 정리
Obsidian 밖에 저장 Obsidian vault 안에 저장
검색 안 해도 됨 나중에 다시 찾아야 함
6

backups/

data/와 artifacts/의 복사본. 복구 우선순위는 db → sessions → artifacts 순.

💾

backups/

$WORKSPACE_ROOT/backups/
git 제외
  • daily/매일 자정 db 스냅샷 + sessions 압축. Raspberry Pi Job Runner가 담당.
  • weekly/주 1회 전체 data/ 압축 백업. 장기 보관.

knowledge/ 백업은?

Obsidian vault는 Git으로 따로 버전 관리하거나 iCloud/Dropbox 동기화를 쓴다. DB처럼 실행 중 손상될 위험이 없어서 별도 스냅샷 백업은 필요 없다.

7

경계 규칙

어떤 파일이 어느 폴더로 가야 하는지 헷갈릴 때 쓰는 판단 기준.

상황 어디로 가나 이유
논문·아티클을 에이전트가 읽고 정리해줬으면 한다 raw/ (또는 raw/{slug}/) LLM wiki ingest 입력. 에이전트가 읽고 knowledge/wiki/에 합성 페이지 생성.
PDF 저장하고 싶다 (내가 직접 참고할 것) knowledge/projects/{slug}/attachments/ Obsidian에서 바로 열고 같은 프로젝트 노트와 연결 가능.
작업 중 떠오른 메모 (프로젝트 명확) knowledge/projects/{slug}/ 해당 프로젝트 폴더에 바로 작성.
작업 중 떠오른 메모 (프로젝트 불명확) knowledge/00_inbox/ 일단 inbox에 넣고, 나중에 projects/ 하위로 승격.
설계 결정을 문서로 남기고 싶다 knowledge/projects/{slug}/adr/ 프로젝트 slug에 맞는 ADR 폴더에 저장. personal-os 시스템 자체 문서는 personal-os/docs/에도 유지.
에이전트가 생성한 파일 artifacts/generated/ 자동 생성물. 검토 후 knowledge로 승격할 수도 있음.
앱 설정, 환경변수 ~/personal-os/.env.local (.gitignore) 코드의 일부. 단, 시크릿은 git에 절대 넣지 않는다. WORKSPACE_ROOT 경로 포함.
DB 파일 $WORKSPACE_ROOT/data/db/ 런타임 데이터. 앱 코드와 분리. git에 넣으면 바이너리 충돌 발생.
가장 자주 헷갈리는 경계는 artifacts/ vs knowledge/다. "나중에 다시 찾아보고 싶은가?" → Yes면 knowledge/, No면 artifacts/. "직접 쓴 것인가, 자동 생성된 것인가?" → 직접 쓴 것은 knowledge/.
